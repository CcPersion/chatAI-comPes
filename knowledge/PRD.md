# PRD：local-ai-companion-v2 本地语音管线重写（VoxCPM2）

## 0. 本轮变更摘要与基线

本轮只重写“回复语音”相关需求：废弃旧的 Qwen3-TTS / CosyVoice 活跃实现，改以 VoxCPM2 作为目标语音合成技术，面向 NVIDIA RTX 5060 Ti 16GB 显存。

本轮需求基线为 Git 提交：`3b808b3d95212bd3b1e27561a6dafa103fa609e7`，提交信息为 `backup: preserve pre-voxcpm voice pipeline`，时间为 2026-08-10。该提交用于保留重写前代码状态，便于对照和回溯。

本 PRD 只定义产品需求、范围、废弃边界和验收标准，不定义 VoxCPM2 的推理框架、量化方式、进程拓扑、队列实现或具体依赖版本；这些属于后续架构与实现阶段。

`CONSTITUTION.md` 当前在仓库中不存在。本轮记录为“待补安全基线”，不假设、不捏造其内容；在该文件补齐并通过安全审查前，不得宣称 Ai-Team 安全门禁已完成。

## 1. 项目背景与目标

### 1.1 背景

- 项目是 Windows 本机运行、浏览器访问的本地真人 AI 语音伴侣。
- 当前语音回复的听感、音色稳定性、句间连续性和实时体验未达到预期，原有 TTS 活跃实现不再作为后续产品路线。
- 目标硬件为 NVIDIA RTX 5060 Ti 16GB；首要目标是在该显存约束下获得可持续的本地语音对话体验，而不是继续堆叠更大的模型。
- 项目仍需保持本地运行、首次准备后可离线运行、单用户单角色、简洁 Web 页面和 LiveTalking/WebRTC 数字人展示。

### 1.2 本轮目标

1. 将 VoxCPM2 定义为唯一的目标 TTS 后端，负责把 LLM 回复文本转换为回复音频。
2. 改善回复音频的自然度、音色一致性、连续播放和首响体验。
3. 在 5060 Ti 16GB 上完成“ASR → LLM → VoxCPM2 → 播放 → LiveTalking/WebRTC 口型展示”的完整本地闭环。
4. 保留并验证已有 ASR、LLM、LiveTalking/WebRTC 能力，不把 TTS 重写扩大为整套 AI 链路重写。

### 1.3 明确概念边界

- **VoxCPM2 是 TTS 技术**：输入文本和声音条件，输出语音；不负责语音识别，不负责对话理解，不替代 LLM。
- **ASR 保留**：继续使用当前 faster-whisper large-v3 语音识别能力，除非后续另立需求。
- **LLM 保留**：继续使用当前 llama.cpp + Qwen3 本地对话能力，除非后续另立需求。
- **数字人链路保留**：wav2lip256、LiveTalking 和 WebRTC 仍在本轮集成范围内，负责把回复音频呈现为口型同步的数字人画面；它们不是 VoxCPM2 的替代品。

## 2. 目标体验

用户点击语音球说话，系统完成：

`麦克风 → VAD → faster-whisper ASR → 本地 Qwen3 LLM → VoxCPM2 TTS → 浏览器播放 → wav2lip256 / LiveTalking / WebRTC`

用户应听到自然、连贯、音色稳定的回复；回复播放过程中，数字人口型应跟随实际播放音频；用户再次说话或点击停止时，旧回复应快速停止，不得残留、重叠或串入下一轮。

## 3. 用户故事

### US-01：自然的本地语音回复（Must）

作为用户，我希望 AI 的回复听起来连贯、自然，不像当前实现那样出现明显机械感、句间断裂或音色漂移。

验收重点：同一声音条件下，多轮回复的音色基本一致；连续段落没有非预期断裂、重复或截断。

### US-02：VoxCPM2 声音条件/克隆（Must）

作为用户，我希望使用本地参考音频让数字人以稳定的目标音色回复。

验收重点：使用清晰、单人、约 5–15 秒参考音频时，盲听者能够稳定辨识目标音色；参考音频质量不足时，系统给出可理解提示，而不是静默失败。

### US-03：完整语音对话闭环（Must）

作为用户，我希望自己的中文语音经过现有 ASR 和本地 LLM 处理后，由 VoxCPM2 生成语音，并在浏览器中听到回复、看到数字人口型同步。

验收重点：VoxCPM2 只承担 TTS，ASR、LLM、播放和数字人链路职责边界清晰，整链路可实际运行。

### US-04：连续播放与低首响（Must）

作为用户，我希望长一点的回复能够连续听完，不需要等待所有文本生成结束，也不出现明显的句间空洞；同时从我说完话到听到 AI 第一段声音的等待时间可接受。

验收重点：首响延迟和音频间隙满足本 PRD 的可测指标。

### US-05：打断与恢复（Must）

作为用户，当 AI 正在说话时，我重新说话或点击停止，系统应快速停止旧回复并进入下一轮，不播放旧音频残留，不让旧回复继续驱动嘴型。

验收重点：音频、播放队列、TTS 后续生成和数字人口型状态都能收敛到新一轮状态。

### US-06：5060 Ti 16GB 可运行（Must）

作为本机用户，我希望在 RTX 5060 Ti 16GB 上运行目标链路时不因显存不足频繁崩溃或无响应。

验收重点：在规定的全链路和连续对话测试中无 OOM；显存峰值可观测、可解释。

### US-07：文字兜底与离线使用（Should）

作为用户，当 ASR 不可用或网络断开时，我仍希望使用文字输入与本地 LLM 对话；TTS 是否输出由运行配置决定，但不能依赖云端服务。

验收重点：断网后，已经准备好的本地模型和依赖仍能完成文字对话及可用的语音回复链路。

### US-08：旧 TTS 不再作为活跃路线（Must）

作为项目维护者，我希望后续验收只针对 VoxCPM2，避免旧 Qwen3-TTS / CosyVoice 路径继续被默认调用或作为“通过”依据。

验收重点：运行时默认路由、配置说明和验收记录均指向 VoxCPM2；旧实现即使暂时保留，也只能作为历史备份或迁移参考。

## 4. 功能范围

### 4.1 本轮包含

- VoxCPM2 TTS 后端的产品级接入需求：文本输入、声音条件/参考音频、音频输出、错误提示和可观测状态。
- TTS 输出与浏览器播放的连续衔接，包含首响、分段/流式输出表现、队列清理和播放完成状态。
- TTS 输出与 wav2lip256、LiveTalking、WebRTC 的集成验收，确保数字人口型跟随实际播放音频。
- 与现有 faster-whisper large-v3 ASR 的接口衔接和回归验证。
- 与现有 llama.cpp + Qwen3 LLM 的接口衔接和回归验证。
- 语音回复过程中的打断、停止、取消和下一轮恢复。
- RTX 5060 Ti 16GB 下的显存、延迟、稳定性和长回复连续性验收。
- 保持现有本地运行、离线可用、单用户单角色、Gradio 页面简洁等产品约束。

### 4.2 明确废弃边界

- Qwen3-TTS 1.7B 不再是活跃 TTS 后端，不得作为默认路由、降级路由或正式验收对象。
- CosyVoice 不再是活跃 TTS 后端，不得作为默认路由、降级路由或正式验收对象。
- 旧 TTS 代码、配置或报告可以暂时留在 Git 备份中，用于回溯、差异分析和迁移；但不得被新实现隐式调用，也不得以“切回旧后端”掩盖 VoxCPM2 验收失败。
- 是否删除、移动或彻底清理旧代码属于后续实现任务；本轮不直接删除代码。

### 4.3 本轮保留但不重写的能力

- ASR：faster-whisper large-v3；本轮只做接口与回归验证。
- LLM：llama.cpp + Qwen3；本轮只做文本流、取消和上下文衔接验证。
- 视觉：wav2lip256、LiveTalking、WebRTC 及现有数字人底图；本轮只验证音频接入后的口型和画面链路。
- 前端：Gradio 基线页面；本轮不升级 React/Next.js，不新增调试或模型参数面板。
- 运行环境：Windows + WSL2 Ubuntu 24.04，本地运行，首次准备后断网可用。

### 4.4 本轮不包含

- ASR 模型更换、LLM 模型更换或对话人格重做。
- Unreal Engine、MetaHuman、Pixel Streaming 3D 路线。
- 云端 TTS、云端 ASR、云端 LLM、远程声音克隆或任何付费推理接口。
- 多用户、多角色、多会话、长期记忆、RAG、移动端或公网部署。
- 通过预录音频或预录视频伪造实时语音、口型或打断效果。
- 以自动化测试替代真人听感、浏览器麦克风、实际播放和数字人口型验收。

## 5. 可验证验收标准

除特别说明外，验收必须在 RTX 5060 Ti 16GB、Windows + WSL2 目标环境、Chrome 或 Edge 最新稳定版进行。冷启动和暖机运行必须分别记录，不得用暖机数据冒充启动性能。

### AC-01：VoxCPM2 活跃路由

- 运行时日志、配置和实际请求链路均能证明回复文本进入 VoxCPM2 并产生播放音频。
- 运行时不得调用 Qwen3-TTS 或 CosyVoice 生成正式回复。
- 旧 TTS 文件若仍存在，必须被明确标记为 legacy/backup，且不能成为默认或隐藏 fallback。
- 证据：配置检查 + 运行日志 + 一次真实语音回复。

### AC-02：完整本地闭环

- 使用中文语音完成至少 10 个固定测试句，均能走通 `VAD → faster-whisper → llama.cpp/Qwen3 → VoxCPM2 → 浏览器播放`。
- 同一轮回复能够送入 wav2lip256，并经 LiveTalking/WebRTC 在浏览器显示数字人画面。
- ASR、LLM、TTS、播放和数字人各阶段均有可关联的请求/会话标识，失败时能指出失败阶段。
- 证据：运行日志 + 浏览器实际操作 + 聊天记录与音频/画面结果。

### AC-03：声音自然度与音色稳定性

- 使用同一参考音频生成至少 10 条短回复和 5 条较长回复，三名评审进行盲听。
- 自然度、清晰度、音色一致性分别按 1–5 分记录；每项平均分不低于 3.5，且不得出现无法理解的严重发音错误。
- 至少 2/3 评审能够在盲听中把回复稳定归属于目标音色；该结果不能只由开发者本人确认。
- 证据：固定测试集、参考音频、录音样本和盲听记录。

### AC-04：音频连续性

- 对至少 5 条包含多句或较长段落的回复进行连续播放测试。
- 除文本本身的有意停顿外，连续音频块之间不得出现超过 300ms 的非预期静音；不得出现重叠、重复、截断、乱序或明显音色跳变。
- 播放结束后，队列必须清空；下一轮不能携带上一轮未播放音频。
- 证据：播放时间戳/音频波形或等价运行记录 + 浏览器实际听感复核。

### AC-05：首响延迟

- 暖机状态下完成至少 20 次中文语音测试，记录“用户结束说话”到“浏览器听到第一段 AI 音频”的时间。
- 目标为 P50 ≤ 2.5 秒、P95 ≤ 4 秒；冷启动另行记录，不得混入暖机统计。
- 若未达目标，必须输出各阶段耗时分解（ASR、LLM 首段、VoxCPM2 首音频、传输/播放），不得只报告总耗时。
- 证据：带时间戳的运行日志 + 统计结果 + 浏览器听感确认。

### AC-06：RTX 5060 Ti 16GB 显存与稳定性

- 在 ASR、LLM、VoxCPM2、wav2lip256、LiveTalking/WebRTC 按目标运行方式启用时，连续完成至少 10 轮语音对话，包含 2 次打断。
- 测试期间不得发生 OOM、无响应或必须人工杀进程才能恢复的显存失败。
- 记录 GPU 显存峰值；目标峰值不超过 15.0 GiB，并保留约 1 GiB 系统运行余量。若实际运行时需要更低负载，必须明确说明牺牲的能力，不得静默改变验收范围。
- 证据：`nvidia-smi` 或等价 GPU 监控记录 + 连续运行日志 + 失败恢复记录。

### AC-07：打断与跨轮恢复

- 在 AI 播放中途进行至少 10 次重新说话或点击停止测试。
- 从用户操作到浏览器音频停止、数字人口型停止的时间 ≤ 500ms；旧 TTS 生成、播放队列和 WebRTC 音频状态不得继续向新一轮泄漏。
- 随后开始的新一轮回复不得出现上一轮尾音、重复句、旧嘴型或串状态。
- 证据：浏览器实际测试 + 前后端取消日志 + 音频/画面观察记录。

### AC-08：ASR、LLM 与视觉能力不被误伤

- 停用或替换 VoxCPM2 之外的任何组件不属于本轮目标；在 VoxCPM2 接入后，现有 ASR 转写、Qwen3 文本回复、LiveTalking/WebRTC 连接仍能通过各自原有回归检查。
- 不能以“VoxCPM2 可单独生成音频”代替完整链路验收。
- 证据：原有回归用例 + 一次端到端浏览器验收。

### AC-09：离线与本地数据边界

- 在模型和依赖准备完成后断开外网，完成至少 3 轮语音对话和 3 轮文字对话。
- 录音、转写、对话、参考音频和 TTS 音频不上传远程服务；日志中不得出现云端 TTS/ASR/LLM 请求。
- 证据：断网实测 + 本机网络请求检查 + 本地文件/日志检查。

### AC-10：浏览器与真人验收边界

- Chrome/Edge 中必须真实验证麦克风采集、播放、打断、WebRTC 画面和口型；仅 HTTP 200、静态页面、正则测试或后端单元测试不视为通过。
- 听感、音频连续性、口型同步和打断体验必须由真人观察/听感复核；自动化结果只能作为辅助证据。
- 证据：浏览器操作记录、截图/录屏或等价可复核记录，以及评审结论。

### AC-11：安全基线状态

- 在 `CONSTITUTION.md` 补齐前，本轮只能报告“安全基线待补”，不得报告 Ai-Team 安全审查已完成。
- 不得从不存在的文件推断安全规则、密钥管理规则或审查结论。
- 后续补齐 `CONSTITUTION.md` 后，必须重新进行与本轮语音管线相关的安全审查。

## 6. 非功能需求

### 6.1 显存与资源

- 目标硬件：RTX 5060 Ti，16GB 显存。
- 满载定义为目标运行方式下 ASR、LLM、VoxCPM2、wav2lip256、LiveTalking/WebRTC 均处于可用状态，而不是只单独运行 TTS。
- 目标 GPU 峰值 ≤ 15.0 GiB；连续对话不得因显存逐轮增长而最终 OOM。
- 任何降级、串行化、卸载或关闭组件的策略都必须在后续实现文档中显式记录，并在验收报告中说明对首响、连续性和功能范围的影响。
- 16GB 系统内存仍是当前项目约束；若实测不足，应记录为阻塞或风险，不得静默扩大硬件假设。

### 6.2 延迟与吞吐

- 暖机首响目标：P50 ≤ 2.5 秒，P95 ≤ 4 秒。
- 首次启动、模型加载、首次生成必须单独记录，不得与暖机指标混报。
- TTS 生成速度应支持实时播放；若不能实时生成，必须明确标记为“非实时缓冲”，不能宣传为完整实时语音。
- 长回复不得强制等待全部文本完成后才开始播放，除非后续架构评估证明这是满足显存或稳定性所必需，并在验收报告中披露。

### 6.3 音频连续性与同步

- 非预期音频间隙 ≤ 300ms；禁止跨段重叠、乱序、重复和截断。
- 音频播放停止后，数字人口型和 LiveTalking 音频状态应在 500ms 内停止。
- 同一轮回复的音色、采样率、声道和播放格式必须保持一致；发生重采样或格式转换时必须可观测。
- 音频连续性验收以实际浏览器播放为准，不能只以服务端生成了 WAV 文件为准。

### 6.4 质量与可观测性

- 每轮对话应能关联用户输入、ASR 结果、LLM 回复、VoxCPM2 生成、播放和数字人推送状态。
- TTS 失败、参考音频不可用、显存不足、播放中断和 WebRTC 断连必须给出可理解的本地错误状态。
- 不得以静默回退到 Qwen3-TTS、CosyVoice 或无声播放来掩盖 VoxCPM2 失败。

### 6.5 本地化、安全与兼容性

- 所有推理和数据处理保持在 Windows + WSL2 本机，不调用云端推理接口。
- 首次下载模型和依赖后，应支持断网运行；模型、参考音频、转写文本和对话记录只保存在本地。
- 服务继续限制在本机访问范围内；具体安全门禁以待补的 `CONSTITUTION.md` 为准。
- 目标浏览器为 Chrome / Edge 最新稳定版，必须支持 WebAudio、麦克风和 WebRTC。

## 7. 风险、待决策与阶段门禁

- VoxCPM2 在 5060 Ti 16GB 上的实际显存、首响和流式表现需要由后续架构/实现阶段实测，不在本 PRD 中预先宣称已验证。
- 参考音频质量、中文文本切分、长回复策略和播放队列会显著影响听感；这些属于后续实现中的可验证变量，不得在需求阶段假设其已经解决。
