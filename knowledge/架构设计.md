# 架构设计：local-ai-companion-v2 语音管线重写

> 本文是 Architect 对 `knowledge/PRD.md` 的实现约束补充。目标是废弃 Qwen3-TTS/CosyVoice 的活跃路由，改为 VoxCPM 本地 TTS；本轮只更新设计与 API 契约，不修改业务代码。
>
> `CONSTITUTION.md` 当前不存在。本设计只记录“安全基线待补”，不伪造 SEC-01~20 的规则、检查结果或通过结论。

## 1. 架构决策摘要

| 决策 | 结论 |
| --- | --- |
| 默认 TTS | **VoxCPM2**。以音质、自然韵律、48kHz 输出、独立参考音频和可控克隆为主目标。 |
| 备用 TTS | **VoxCPM1.5**。显存余量不足、VoxCPM2 实测不稳定或需要更低延迟时显式切换。 |
| 明确废弃 | Qwen3-TTS、CosyVoice、Edge TTS 不再是活跃路由、fallback 或验收对象；旧代码只留在 Git 备份中。 |
| LLM/ASR/数字人 | 保留 faster-whisper large-v3、llama.cpp/Ollama-compatible Qwen LLM、wav2lip256、LiveTalking/WebRTC。 |
| GPU 原则 | 单用户、单活跃生成、有限队列；所有重模型通过 GPU 预算和代际取消协调，硬门槛是峰值不超过 15 GiB。 |
| 流式原则 | 交互路径只能使用 VoxCPM `generate_streaming`；LLM 按短句提交文本，TTS 按音频块即时发送，不等待整段回复，不用逐段 WAV 覆盖播放器。 |
| 离线原则 | 运行时只读本地模型、依赖和参考音频；禁止首次请求时联网下载或调用云端语音服务。 |

## 2. VoxCPM1.5 与 VoxCPM2 的架构评估

官方版本表给出的近似约束如下；其中 VRAM 和 RTF 是上游在 RTX 4090 上的参考值，不是 RTX 5060 Ti 的实测保证，必须在本机重新测量。

| 维度 | VoxCPM1.5 | VoxCPM2 | 对本项目的意义 |
| --- | --- | --- | --- |
| 模型定位 | Stable，双语中文/英文 | Latest，多语种主线 | 本项目中文为主，两者均可用；2 的扩展能力更强。 |
| 规模/显存 | 上游表约 0.6B backbone、约 6GB VRAM | 2B、约 8GB VRAM | 5060 Ti 16GB 不能默认把 2 与完整 Qwen/LiveTalking 同时满载。 |
| 原生采样率 | 44.1kHz | 48kHz | 2 更适合作为浏览器高质量主音频；送 LiveTalking 时仍需明确适配采样率。 |
| LM token rate | 6.25Hz | 6.25Hz | 两者都适合连续块式生成，不应误称为“逐字符神经流”。 |
| 克隆模式 | continuation only；参考音频必须作为延续提示 | isolated reference + continuation；支持独立参考、可控克隆和 voice design | 2 更容易把“参考音频”和“目标文本”解耦；1.5 要求更严格的参考文本/延续关系。 |
| 流式 | `generate_streaming` | `generate_streaming`，并有更完整的服务生态 | 两者都能提供真实的模型音频块；真正的首响仍取决于文本分句、队列和显存调度。 |
| 参考音频 | 推荐清晰单人声 + 准确转写 | 可使用参考音频与准确文本；ultimate cloning 可同时提供 prompt/reference | 上传校验和 reference text 都是产品输入，不是可选的“调试字段”。 |
| 主要风险 | 音色/韵律能力较低一档，但更省显存 | 显存余量、模型生态和结果稳定性需在本机验证；可控生成跨次可能有差异 | 不能仅凭官方 benchmark 宣称本产品已经通过真人听感验收。 |

**推荐策略：**

1. 默认模型为 VoxCPM2，配置名和健康检查必须显示 `VoxCPM2`，不允许在失败后悄悄切回旧 TTS。
2. 备用模型为 VoxCPM1.5，作为独立 profile `safe-v15`。是否自动降级必须由配置明确开启，并在 `model.selected`/健康检查/日志中记录实际版本。
3. 先实现 VoxCPM2 的完整契约和验收，再做 VoxCPM1.5 的同契约替换；两个版本不能在同一请求中混合生成。
4. VoxCPM2 仍是本轮产品验收的默认对象；VoxCPM1.5 通过的是“兼容运行/显存保底”门，而不是自动覆盖 VoxCPM2 音质门。

官方依据：

- [OpenBMB/VoxCPM 官方版本表与指标](https://github.com/OpenBMB/VoxCPM#-models--versions)
- [VoxCPM2 官方模型卡](https://huggingface.co/openbmb/VoxCPM2)
- [VoxCPM1.5 官方模型卡](https://huggingface.co/openbmb/VoxCPM1.5)

## 3. 现有实现边界与迁移目标

CodeGraph 对当前代码的调用路径确认如下：

```text
voice.yaml
  -> outputs/backend/app.py 配置读取
  -> _get_tts()
       TTS_BACKEND=edge       -> EdgeTTSEngine
       TTS_BACKEND=cosyvoice  -> CosyVoiceTTSEngine
       其他                    -> TTSEngine（旧 Qwen3-TTS）
  -> pipeline.process_text()
  -> audio 事件
  -> _flush_avatar_audio()
  -> forward_audio_to_avatar()
  -> POST avatar-sync.js /api/audio
  -> POST LiveTalking /humanaudio
  -> wav2lip256 / WebRTC
```

旧路径有三个架构问题：

- 活跃后端由 `TTS_BACKEND` 多分支决定，CosyVoice 仍是当前配置默认值，不能作为 VoxCPM 验收基础。
- 旧 UI 逻辑按 Qwen/Edge 分支处理音频，存在“逐段生成但播放器/桥接时序由 Gradio 事件拼接”的耦合；这不是统一的音频块协议。
- 当前桥接接收 `sample_rate` 后直接转发，不能把 VoxCPM2 的 48kHz 音频误标成 16kHz；浏览器播放和 LiveTalking 驱动必须经过明确的 sink adapter。

迁移后的业务代码目标不是继续扩展 `TTSEngine` 分支，而是建立单一的 `VoxCPMWorker` 契约：

```text
Gradio/浏览器
  -> ConversationOrchestrator
       -> faster-whisper（已有，保留）
       -> llama.cpp/Ollama-compatible Qwen（已有，保留）
       -> clause queue
       -> VoxCPMWorker（唯一活跃 TTS）
            -> BrowserAudioSink（原生采样率）
            -> AvatarAudioAdapter（重采样后）
                 -> avatar-sync.js
                      -> LiveTalking / wav2lip256 / WebRTC
```

## 4. 系统组件、职责和边界

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| 浏览器/Gradio UI | 麦克风、文字输入、文字流、AudioWorklet 环形缓冲、停止/打断 | 不直接加载 TTS 模型，不决定模型版本。 |
| faster-whisper large-v3 | 用户语音转文字、VAD 后的最终转写 | 不做 TTS，不把中间 ASR 当成已确认文本。 |
| llama.cpp/Ollama-compatible Qwen | 生成回复文本流 | 不生成音频、不持有参考音频。 |
| ConversationOrchestrator | 会话代际、LLM 文本分句、队列、取消、事件关联 | 不实现具体声学推理。 |
| VoxCPMWorker | 本地加载一个 VoxCPM 版本、参考音频预处理、`generate_streaming`、音频块输出 | 不做 ASR、LLM、数字人渲染。 |
| ReferenceStore | 参考音频、校验结果、文本和指纹的本地存储 | 不上传云端，不把完整路径返回浏览器。 |
| BrowserAudioSink | 原生 44.1/48kHz PCM 的连续播放、jitter buffer、立即停止 | 不为每个块创建独立 HTML audio 元素。 |
| AvatarAudioAdapter | 将同一代音频按 LiveTalking 契约重采样/封装、按序发送 | 不重新合成、不改音色、不吞掉取消代际。 |
| avatar-sync.js | 本地音频转发和 WebRTC 信令中继 | 不猜测采样率，不接受过期 generation。 |
| LiveTalking/wav2lip256 | 音频驱动口型并通过 WebRTC 推送画面 | 不决定 TTS 音频来源。 |

## 5. TTS Worker 设计

### 5.1 模型加载

- Worker 是独立本地进程或独立服务，避免 Gradio 进程持有 CUDA 模型、模型异常拖垮 UI，也避免旧 TTS 类被隐式复用。
- 启动参数只接受本地绝对/规范化模型目录。使用等价于 `VoxCPM.from_pretrained(local_path, load_denoiser=False)` 的本地加载；运行时不得自动从 Hugging Face/ModelScope 下载。
- 启动前检查模型 manifest、代码版本、权重文件大小和 SHA256；缺文件返回 `TTS_MODEL_001`，不进入半就绪状态。
- 交互档默认关闭 `retry_badcase` 或将其限制为可取消模式。官方重试策略可能在坏例上继续生成，不能阻塞用户打断；重试只可作为离线诊断开关。
- 预热使用固定短句和已验证参考音频，预热完成后才报告 `ready`。预热期间健康检查返回 `warming`，不伪装成可服务。
- 参考音频处理后缓存 prompt embedding/编码结果；切换 reference_id 时使缓存失效。缓存键至少包含模型版本、音频 SHA256、参考文本 SHA256 和采样率。

### 5.2 参考音频和文本

默认采用 `ultimate` 克隆输入：

- VoxCPM2：`prompt_wav + prompt_text`，并在需要最大相似度时同时使用同一音频作为 `reference_wav`；这是 VoxCPM2 的独立参考/延续能力，不是旧 Qwen 的 prompt 约定。
- VoxCPM1.5：使用 continuation 模式，要求参考音频与 `prompt_text` 严格对应；不宣称具备 VoxCPM2 的 isolated reference 能力。
- 参考音频建议 5–15 秒、单人、低噪声、无背景音乐、无明显混响。上传时检查容器、可解码性、时长、声道、峰值、静音比例和文本是否为空；内部统一转为模型要求的单声道参考格式。
- 参考音频和转写文本只保存在本机；日志只记录 `reference_id`、哈希和统计，不记录完整音频、声纹特征或用户原始文本。

### 5.3 真正流式输出

“真正流式”在本项目中定义为：

1. Qwen LLM token 到达后，由 Orchestrator 按中文标点、短语边界或长度阈值提交一个 `text_unit`；不等整轮回复。
2. 每个 `text_unit` 只启动一个 VoxCPM `generate_streaming`，其生成的每个音频块立即发送给下游；交互路径禁止调用整段 `generate` 后再切 WAV。
3. TTS 队列只允许一个 active generation 和最多一个待处理 `text_unit`。待处理项被取消时不得进入模型。
4. 浏览器使用一个持续的 AudioWorklet/ring buffer；块按 `sequence` 追加，不能用多个 Gradio `Audio` 更新制造拼接间隙。
5. 音频块必须包含 `generation_id`、`sequence`、`sample_rate`、`duration_ms` 和 `is_first/is_last`。下游发现代际不匹配必须丢弃，不得播放。

这仍然不是“逐字符端到端 TTS”：VoxCPM 需要一个已提交的文本单元。产品可以声称“模型原生音频块流式 + LLM 短句增量”，不能声称“LLM 每个 token 立即变成音频”。

### 5.4 队列、取消和打断

```text
conversation_id
  -> generation_id（每轮递增）
       -> text_unit sequence
            -> audio sequence
```

- 新一轮用户输入或停止按钮会原子地递增 `generation_id`，取消 LLM、TTS、浏览器播放和 avatar 发送队列。
- 取消首先设置线程/任务取消令牌；Worker 在每个音频块边界检查令牌，并停止向外发送。
- VoxCPM 单次 CUDA kernel 无法被 API 直接抢占时，允许当前块结束；超过取消预算才回收 Worker 子进程。禁止为了取消而强制杀掉主 UI 或 LiveTalking。
- 取消后清空 active/pending 音频队列；桥接端按 generation 丢弃晚到块。目标从用户操作到浏览器静音/数字人闭嘴 ≤500ms，实际值必须测量。
- 正常模式不允许多并发 TTS。队列深度超过 1 返回 `TTS_QUEUE_001` 或取消最旧未开始项，不能静默排队造成旧回复串音。

## 6. RTX 5060 Ti 16GB 显存隔离方案

### 6.1 预算原则

PRD 的硬门槛是峰值 ≤15 GiB，剩余约 1 GiB 给驱动、CUDA allocator、浏览器和系统波动。官方 VoxCPM 近似显存不是完整链路预算，必须以 `nvidia-smi` + PyTorch allocator 峰值为准。

| 配置档 | VoxCPM | LLM 策略 | 适用 |
| --- | --- | --- | --- |
| `balanced-v2`（默认） | VoxCPM2 CUDA，关闭 denoiser，交互步数先从 10 开始 | Qwen3-8B 量化/受限 GPU offload；给 TTS 和 LiveTalking 预留预算 | 追求音质；必须通过本机峰值门禁。 |
| `safe-v15`（备用） | VoxCPM1.5 CUDA | 同上，可保留更多 LLM/LiveTalking 余量 | VoxCPM2 OOM、首响/连续性不达标或显存峰值超门槛。 |
| `exclusive`（故障保底） | 仅一个重模型占用 GPU；LLM 与 TTS 通过 lease 串行 | 必要时降低 LLM GPU layers 或让 LLM 走 CPU | 牺牲吞吐和首响，换取不崩溃；必须在状态与日志中显示。 |

实施要求：

- 启动时测量空闲 GPU、LiveTalking、ASR 和 LLM 的基线，再加载 VoxCPM；不能把“官方约 8GB”直接当作可用预算。
- GPU Lease Manager 只允许一个 TTS generation；LLM 生成和 LiveTalking 的 GPU 使用必须受预算/并发约束。`torch.cuda.empty_cache()` 不是隔离策略，不能代替进程和预算管理。
- `llama-server` 不能以无限 GPU offload 运行。优先固定 Qwen3-8B 量化档和 `n_gpu_layers`/KV cache 上限；Qwen3-14B 不作为 5060 Ti 16GB 默认组合。
- 若实测 `VoxCPM2 + Qwen + LiveTalking` 峰值超过 15 GiB，优先切换 `safe-v15`；若仍超限，进入 `exclusive`，不得继续堆叠模型或隐式切回旧 TTS。
- 自动降级必须写入 `model.selected`, `model.reason`, `gpu_peak_gib`；健康接口必须让前端和验收日志看到实际模型。
- 每轮结束释放临时音频 tensor、清理过期队列和引用；连续 10 轮观察显存不应单调增长。

### 6.2 负载与质量取舍

- VoxCPM2 原生 48kHz 音质保留到浏览器播放；交互步数、CFG、temperature、seed 是可观测参数，不在 UI 暴露调试面板。
- LiveTalking 只消费它明确支持的采样率；若当前 `/humanaudio` 链路是 16kHz，则在 `AvatarAudioAdapter` 显式重采样，不能把 48kHz/44.1kHz PCM 只改 header 冒充 16kHz。
- 浏览器和口型驱动必须从同一代、同一顺序的音频块派生。允许两路各自格式化，但不允许二次 TTS 或使用不同版本的音频。
- 首响优化顺序：预热模型 → 缓存参考 prompt → LLM 短句提交 → VoxCPM 首块 → 浏览器 jitter buffer；不能用播放未完成的“占位音”伪造真人回复。

## 7. 采样率、音频格式和 LiveTalking 适配

| 链路 | 格式 |
| --- | --- |
| VoxCPM2 输出 | mono PCM，原生 48,000 Hz；内部块不带 WAV 头，首尾由事件标记。 |
| VoxCPM1.5 输出 | mono PCM，原生 44,100 Hz；不得强行按 48kHz 声明。 |
| 浏览器播放 | 保持模型原生采样率，由 AudioWorklet/ring buffer 播放。 |
| LiveTalking 输入 | 由 AvatarAudioAdapter 根据 LiveTalking 实测契约输出；当前旧链路按 16kHz 处理时，明确重采样到 16kHz mono PCM/WAV。 |
| avatar-sync | 每个请求携带真实 `sample_rate`、`generation_id` 和 `sequence`；桥接不得猜测或覆盖。 |

口型对齐不以“HTTP 200”作为通过条件。必须验证浏览器实际听到的音频与 LiveTalking 收到的同一代音频顺序一致，并在真实浏览器中观察嘴型跟随、停止和重说。

## 8. 离线边界和本地数据

- 安装阶段允许人工下载 `voxcpm` Python 包、模型权重、CUDA/torch 依赖和 LiveTalking 依赖；应保存版本锁定和文件校验信息。
- 运行阶段禁止模型自动下载、遥测、云端 TTS/ASR/LLM、远程 voice cloning API；网络只用于本机端口通信。
- 离线就绪条件是：VoxCPM 权重、VoxCPM Python 依赖、参考音频、ASR、Qwen LLM、LiveTalking 和浏览器本地资源均已存在。缺任何一项都应报告具体阶段未就绪。
- 参考音频、转写、音频缓存和日志默认只写本机指定目录；日志不得写完整音频 base64。

## 9. 可观测性

每个请求必须贯穿 `request_id`、`conversation_id`、`generation_id`、`model_id` 和 `reference_id`（只记录指纹/短 ID）。至少记录：

- 排队时间、模型开始时间、首音频块时间、最后音频块时间、浏览器开始/结束播放时间。
- LLM 首 token、首个 text_unit、TTS 首块、各块序号/时长、总音频时长、队列深度。
- 设备、模型版本、采样率、CFG、推理步数、seed（如使用）、峰值显存、取消原因和错误码。
- 断流、丢块、乱序、代际丢弃、LiveTalking 转发延迟和 WebRTC 断开。

日志分级为 `INFO/WARN/ERROR`；默认不记录用户原始录音、完整参考文本或完整模型回复。健康接口返回运行状态，不返回模型绝对路径和内部堆栈。

## 10. 验收门和风险

架构阶段只定义门，不宣称已经通过：

1. VoxCPM2 默认路由证据：配置、启动日志、健康接口和一次真实音频都指向 VoxCPM2。
2. 5060 Ti 16GB：冷启动/暖机、10 轮对话、至少 2 次打断，峰值 ≤15 GiB，无 OOM 或人工杀进程恢复。
3. 流式：首块时间、块序列和浏览器实际播放可见；不能只检查 HTTP 200 或最终 WAV 文件。
4. 连续性：至少 5 个多句回复，非预期静音 ≤300ms，无重叠、乱序、重复和音色跳变。
5. 克隆：同一参考音频 + 精确参考文本，10 条短句和 5 条长句，至少 3 人盲听评分；不得把开发者自听作为唯一证据。
6. LiveTalking/WebRTC：真实浏览器中听感、口型、停止、重说分别复核。
7. 离线：断网后完成文字和语音闭环；日志没有云端请求。

主要风险：VoxCPM2 官方显存数字与本机组合不同；VoxCPM1.5 的 continuation 约束会放大参考文本错误；VoxCPM 生成跨次稳定性需要本地测量；LiveTalking 采样率和时钟若不明确会造成口型不同步；打断只能在块边界可靠生效。Developer 必须按 API 契约实现并回填实测值。

## 11. 安全基线状态
