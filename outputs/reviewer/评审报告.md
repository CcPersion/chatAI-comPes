## 正确性 (55/100)

### 具体理由

**1. 致命缺陷：状态机 cancel_event 逻辑错误导致语音管线无法执行 LLM 流式回复 (app.py L176-186, L826-855)**

`AvatarStateMachine.transition()` 在进入 LISTENING 或 IDLE 状态时无条件设置 `cancel_event`（L181-182）。在 `process_voice()` 正常流程中：

```
L826: reset_cancel()           → cancel_event.clear()
L829: transition(LISTENING)    → cancel_event.set()   ← 唤醒即设置！
L833: transition(THINKING)     → 不改变 cancel_event（仍为 set）
L837: ASR 执行                  → 不检查 cancel_event
L854: stream_chat(cancel)      → L462 if cancel_event.is_set(): break  ← 立即中断！
```

后果：语音管线的 LLM 流在第一轮检查时就被打断，`full_reply` 始终为空，语音对话闭环完全失效。`process_text()` 不受影响（其首次状态转换是 IDLE->THINKING，不触发 cancel_event 设置）。这是一个 P0 级别的阻塞性缺陷，任何包含 LLM 流式回复的语音对话都无法执行。

**修复方向**（二选一）：
- 方案A：`transition()` 中仅当 `old_state` 为活跃状态（SPEAKING/THINKING）且 `new_state` 为打断状态（LISTENING/IDLE）时才设置 cancel_event。
- 方案B：`process_voice()` 中在 LLM 流式调用前增加一次 `state_machine.reset_cancel()` 调用（在 L851 之前）。

**2. Bug-004 (Major): handle_stop() 破坏聊天记录 (app.py L1274-1277)**

`handle_stop()` 返回 `("已停止", "待机")` 两个字符串。第一个返回值直接映射到 `outputs=[chatbot, status_text]` (L1342-1346)。`gr.Chatbot` 期望接收 `List[List[str]]`（对话历史列表），但实际收到的是纯字符串 `"已停止"`。这会导致：
- 聊天记录被替换为纯文本 "已停止"，全部对话历史丢失
- Gradio chatbot 状态异常，后续对话可能渲染错误
- 直接违反 AC-06（打断不破坏对话历史）和 AC-10（连续对话稳定性）

**3. Bug-005 (High): 文字兜底场景 TTS 音频被丢弃 (app.py L1265-1267)**

`handle_text_input()` 中 `event["type"] == "audio"` 分支仅写 `pass`，未将 TTS 音频数据传递给任何音频输出组件。`handle_text_input` 的 outputs 列表仅含 `[text_input, chatbot, status_text]`，不含 `gr.Audio` 组件。这意味着：
- 文字输入场景下 TTS 合成虽然执行，但音频数据在 Python 进程内被丢弃
- 前端无法收到 TTS 语音播放
- 直接违反 AC-08（文字兜底时 TTS 按配置可选播放）

### 其他发现

- **4 状态转换设计正确**：IDLE/LISTENING/THINKING/SPEAKING 枚举 (L138-142) 与架构设计 §2 一致，`threading.Lock` 保证线程安全 (L152)。

### Bug-001: 配置键 TTS_MODEL 与 TTS_MODEL_PATH 命名不一致

- **核实结论**: 确认存在
