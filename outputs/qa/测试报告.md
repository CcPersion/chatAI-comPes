## 2. 安全合规检查 (SEC-02/03/04/05/11/12/17/18)

### SEC-02: 禁止 eval()/exec()/Function()

**检查方法**: 在 app.py 中搜索 `eval(`, `exec(`, `compile(`, `Function(`，以及 `__import__`, `globals()`, `locals()`。

**结果**:
- app.py: 搜索结果为 0。代码仅在注释 (L1411) 中出现 "eval()/exec()" 字样。
- avatar-sync.js: 搜索 `eval(`, `Function(`, `new Function(` — 未发现。使用 `crypto.randomUUID()` 为内置安全 API。

**结论**: ✅ **通过** — 无动态代码执行。

### SEC-03: 禁止命令注入（子进程调用用参数数组）

**检查方法**: 在 app.py 中搜索 `os.system`, `subprocess.Popen`, `subprocess.call`, `subprocess.run`, `shell=True`, 以及 `$(` / `` ` `` 构造。

**结果**:
- app.py: `subprocess` 未导入。无 `os.system()`。所有外部调用通过 httpx/requests 库，URL 来自 voice.yaml 配置，不拼接用户输入。faster-whisper / Qwen3-TTS 通过 Python API 直接调用。
- avatar-sync.js: 使用 Node.js `http.request()` 原生方法，URL 来自 CONFIG 对象，未使用 `child_process.exec()` 或 `execSync()`。
- start-llama.bat: 使用 `start "llama-server" "%LLAMA_SERVER%" --model "%MODEL_PATH%" --host %HOST% --port %PORT% -ngl 999 ...`。路径来自脚本内变量，不涉及用户输入。
- install-voice.sh: 使用 `python3 -c "..."` 执行固定代码字符串（不含外部变量拼接），`pip install -r "$REQUIREMENTS_FILE"` 使用固定文件路径。

**结论**: ✅ **通过** — 无 shell 注入向量。外部命令均使用参数数组/API 方式，无用户输入拼接。

### SEC-04: HTML 转义防 XSS

**检查方法**: 检查 LLM 回复文本渲染路径。

**结果**:
- app.py: LLM 回复通过 `gr.Chatbot` 组件显示，Gradio 默认对 chatbot 内的 Markdown 做安全转义（HTML 标签会被转义）。
- avatar_video: 使用 `gr.HTML` 组件，内容为静态 HTML 字符串（L1101-1111），不含模型输出或用户输入。
- connection_html: 通过 `update_connection_status()` 生成，HTML 内容仅包含固定的 CSS class 和状态文本（status 字符串来自字典映射，不含用户输入）。
- 自定义 CSS: 纯 CSS 字符串，不含用户输入。
- avatar-sync.js: 仅做数据转发，不渲染 HTML。

**结论**: ✅ **通过** — Gradio 默认安全转义 + 无 innerHTML 插模型输出。

### SEC-05: 文件路径校验防路径遍历

**检查方法**: 审查 handle_audio_upload() 和 validate_ref_audio() 的路径处理。

**结果**:
- `handle_audio_upload()` (L719): 使用 `os.path.basename()` 剥离目录路径，仅保留文件名部分。
- `handle_audio_upload()` (L720): 使用 `hashlib.sha256()` 生成安全文件名，消除用户控制的文件名。
- `validate_ref_audio()` (L680-684): 使用 `os.path.realpath()` 解析符号链接后，验证最终路径以 `UPLOAD_DIR + os.sep` 开头。
- UPLOAD_DIR 来自配置 `~/setup/uploads/`，由 `os.path.expanduser()` 展开，不直接接受用户输入作为目录路径。

**结论**: ✅ **通过** — 多层防护: basename 剥离 + SHA256 重命名 + realpath 验证。

### SEC-11: 异常不暴露堆栈

**检查方法**: 审查所有异常处理路径，验证前端返回的消息是否包含 Python 堆栈。

**结果**:
- `PipelineError`: 携带用户可理解的 message 字段。to_dict() 中 detail 默认为 "详见本地日志"。
- `error_response()` (L119-130): 在日志中记录错误码和消息，detail 默认 "详见本地日志"。
- `handle_audio_input()` (L1232-1235): 外层 except Exception 捕获后返回 "处理失败，请重试"。
- `handle_text_input()` (L1268-1270): 同上。
- `LLMClient.stream_chat()` (L489-491): 通用 Exception 转换为 LLM_ERR_003 "大模型回复超时，请重试"。
- avatar-sync.js: `/health` 端点异常被 catch 后仍返回 200 (L195-204)。POST /api/audio 异常返回 `LIP_ERR_001` (L269-276)。错误消息不含内部路径或堆栈。
- ⚠️ **潜在问题**: handle_audio_input() / handle_text_input() 的 except Exception 块中使用 `traceback.format_exc()` 写日志（允许），返回给用户的是 "处理失败，请重试"，不暴露堆栈。但在 handle_audio_input 的 for event 循环中 (L1216-1231)，如果 pipeline.process_voice() 生成器中某个未被捕获的异常导致事件流中断，会传播到外层 except。
- ⚠️ show_error=True (L1399): Gradio 的 show_error 参数为 True 时，Gradio 自身异常（如组件渲染错误）可能会显示堆栈。但这属于 Gradio 框架行为，非本项目代码问题。

**结论**: ✅ **通过** — 自定义代码层面堆栈保护到位。Gradio show_error 属框架风险，可接受。

### SEC-12: 文件上传校验类型与大小

**检查方法**: 审查 validate_ref_audio() 全部校验逻辑。

**结果**:
| 校验项 | 实现 | 值 |
| --- | --- | --- |
| 扩展名白名单 | L688: `if ext not in ALLOWED_AUDIO_EXTENSIONS` | `["wav", "mp3", "m4a", "flac"]` |
| 文件大小上限 | L692-694: `if size_mb > MAX_UPLOAD_SIZE_MB` | 15 MB |
| 音频时长下限 | L701-702: `if duration < MIN_REF_AUDIO_SEC` | 5 秒 |
| 音频时长上限 | L701-702: `if duration > MAX_REF_AUDIO_SEC` | 15 秒 |
| 路径安全检查 | L680-684: realpath 验证 | 见 SEC-05 |

- ⚠️ 音频 MIME 类型魔术字节校验缺失。当前仅依赖扩展名白名单，攻击者可将恶意文件后缀改为 .wav 绕过。soundfile 在读取时会因格式非法而失败，但最佳实践建议增加 `file` 命令或 `python-magic` 校验魔术字节。

**结论**: ⚠️ **条件通过** — 扩展名/大小/时长校验完备，但缺少魔术字节(MIME type)校验。风险等级低（soundfile/sf.info() 会因非法格式失败 + 文件仅本地处理）。

### SEC-17: API 响应不过度暴露字段

**检查方法**: 审查自定义接口的响应体字段。

**结果**:
- `get_service_status()` (L233-243): 仅返回状态字符串 ("connected"/"disconnected"/...)，不暴露模型路径、内部配置、端口外的细节。
- `handle_audio_upload()` (L745-749): 返回 `{ok, message, file_id}`。file_id 为 SHA256 哈希前缀，不暴露实际文件系统路径。
- `error_response()` (L119-130): 返回 `{error: {code, message, detail}}`。detail 默认 "详见本地日志"。
- `update_connection_status()` (L1289-1312): HTML 内容仅显示服务名和状态字符串，不泄露端口号以外的配置。
- avatar-sync.js GET /health (L186-194): 返回 `{status: "ok", service: "avatar-sync", upstream: "livetalking:ok"}` — 符合 API契约 §5.3。
- ⚠️ **轻微问题**: app.py 启动日志 (L1383-1385) 输出 TTS_MODEL_PATH 和 UPLOAD_DIR 完整路径到 stdout。在 Gradio 控制台可见，但不暴露到前端。符合 "本地日志可查" 的约定。

**结论**: ✅ **通过** — 所有自定义接口未过度暴露内部信息。

## 7. Bug 清单

### [Bug-001] 配置键 TTS_MODEL 与 TTS_MODEL_PATH 命名不一致

- **严重度**: Major
- **关联**: AC-02 (全链路语音对话), API契约 §4.6
- **描述**: API契约 §4.6 定义的配置键名为 `TTS_MODEL`，但 voice.yaml (L59) 和 app.py (L84) 实际使用的键名为 `TTS_MODEL_PATH`。两者语义相同（表示模型路径），但键名不一致会在按契约查找配置时导致读取失败。
- **复现步骤**:
  1. 按 API契约编写自动化测试，查找 voice.yaml 中的 `TTS_MODEL` 键
  2. 键不存在，测试失败
- **预期**: 键名统一为 `TTS_MODEL` 或 `TTS_MODEL_PATH`
- **实际**: API契约为 `TTS_MODEL`，代码为 `TTS_MODEL_PATH`
- **建议**: 统一使用 `TTS_MODEL_PATH`（更明确表达是路径），并更新 API契约 §4.6。

### [Bug-002] CFG_ERR_001 错误码未按统一格式实现

- **严重度**: Minor
- **关联**: AC-01 (一键启动), API契约 §7.2
- **描述**: API契约 §7.2 定义了 `CFG_ERR_001` 错误码用于配置非法场景。但 app.py 的 `find_config()` 在找不到配置文件时抛出标准 `FileNotFoundError`，未经 `PipelineError("CFG_ERR_001", ...)` 包装，也未使用统一的 `{"error": {"code": ...}}` 格式。API实现说明.md 第 127 行声称 CFG_ERR_001 已实现，但实际未包装。
- **复现步骤**:
  1. 删除或移动 voice.yaml 到所有搜索路径之外
  2. 启动 app.py
  3. 观察输出
- **预期**: 错误响应为 `{"error": {"code": "CFG_ERR_001", "message": "配置文件有误，请检查 voice.yaml"}}`
- **实际**: 抛 `FileNotFoundError: 找不到 voice.yaml。请将 config/voice.yaml 复制到 ~/setup/ 或项目根目录。`（非统一格式）
- **建议**: 在 find_config() 内部捕获 FileNotFoundError 并包装为 PipelineError("CFG_ERR_001", ...)。

### [Bug-003] start-voice.sh 注释与实际监听地址不一致

- **严重度**: Minor
- **关联**: AC-01 (一键启动)
- **描述**: start-voice.sh 第 70 行注释声明 "监听: 0.0.0.0:7860 (Gradio 默认，WSL2 localhost 转发对 Windows 可见)"，但 app.py 第 1396 行实际设置 `server_name="127.0.0.1"`。两者描述相反，可能误导运维人员排查网络连通性问题。
- **复现步骤**:
  1. 阅读 start-voice.sh 注释，期望 Gradio 监听 0.0.0.0
  2. 启动服务后检查监听地址
- **预期**: 注释与实际代码一致
- **实际**: 注释说 0.0.0.0，代码绑 127.0.0.1
- **建议**: 更新 start-voice.sh 注释为 "监听: 127.0.0.1:7860（仅本地访问，WSL2 localhostForwarding 对 Windows 可见）"。

### [Bug-004] handle_stop() 返回格式破坏 chatbot 内容

- **严重度**: Major
- **关联**: AC-06 (打断), AC-10 (连续对话稳定性)
- **描述**: app.py 第 1274-1277 行的 `handle_stop()` 函数返回 `("已停止", "待机")`，其中第一个返回值直接覆盖 `chatbot` 组件。Gradio 中 `gr.Chatbot` 期望接收 `List[List[str]]` 格式（对话历史列表），但 `handle_stop()` 返回了一个字符串 `"已停止"`。这会导致：
  1. chatbot 显示内容被替换为纯文本 "已停止"，丢失全部对话历史
  2. 操作后继续对话时 chatbot 状态异常
- **复现步骤**:
  1. 进行一轮对话，chatbot 中有用户消息和 AI 回复
  2. 点击 "停止" 按钮
  3. 观察 chatbot 是否被清空或变成 "已停止" 文本
- **预期**: 点击停止后 chatbot 内容保持不变，仅状态文字更新为 "已停止"
- **实际**: chatbot 被替换为字符串 "已停止"
- **建议**: handle_stop() 不应修改 chatbot 内容，或者通过 gr.State 保持历史。修改为 `return gr.skip(), "待机"` 跳过 chatbot 更新，或返回当前 chatbot 状态而非字符串。

### [Bug-005] 文字兜底场景 TTS 音频数据被丢弃

- **严重度**: High (影响 US-06 完整功能)
- **关联**: AC-08 (文字兜底)
- **描述**: app.py 第 1265-1267 行，`handle_text_input()` 在处理 `event["type"] == "audio"` 时，仅写了 `pass` 和注释 "音频播放由 Gradio 音频组件处理后自动播放"。但实际上这个 yield 的 audio 事件（包含 (sample_rate, audio_data)）没有被传递给任何 Gradio 音频输出组件。`handle_text_input()` 的 outputs 列表中仅包含 `[text_input, chatbot, status_text]`，不包含任何音频输出组件。因此，文字兜底场景下 TTS 合成的音频虽然生成了，但前端无法收到并播放。
- **复现步骤**:
  1. 停用 ASR，使用文字输入发送消息
  2. 观察是否有 TTS 语音播放
- **预期**: 文字兜底时 TTS 语音正常播放（若配置启用）
- **实际**: TTS 音频被生成但未传递给前端播放
- **建议**: 
  1. 将 `gr.Audio` 输出组件加入 `handle_text_input` 的 outputs
  2. 或将音频数据通过其他方式（如 WebSocket / 内嵌 `<audio>` 标签）推送给前端
  3. 或在 `handle_text_input` 中 yield audio 时更新一个隐藏的 gr.Audio 组件

### [Bug-006] voice.yaml 中 LOG_LEVEL 和 LOG_DIR 未被 app.py 使用

- **严重度**: Minor
- **关联**: US-09 (参数可调)
- **描述**: voice.yaml 定义了 `LOG_LEVEL: "INFO"` (L87) 和 `LOG_DIR: "~/setup/logs"` (L91)，但 app.py 第 41-46 行的 `logging.basicConfig` 硬编码使用 `level=logging.INFO` 和 `handlers=[logging.StreamHandler(sys.stdout)]`，不从 voice.yaml 读取这两个配置项。用户修改 voice.yaml 中的日志相关配置将不生效。
- **复现步骤**:
  1. 修改 voice.yaml 中 LOG_LEVEL 为 "DEBUG"
  2. 重启 app.py
  3. 观察日志级别
- **预期**: 日志级别变为 DEBUG
- **实际**: 仍为 INFO（硬编码）
- **建议**: 在配置加载后读取 LOG_LEVEL 和 LOG_DIR，传递给 logging.basicConfig 或使用 dictConfig。

### [Bug-007] requirements.txt 中 `huggingface-cli` 版本无效

- **严重度**: Minor
- **关联**: 依赖安装 (install-voice.sh)
- **描述**: requirements.txt 第 47 行 `huggingface-cli==0.0.0`，注释说 "通过 huggingface_hub 提供"。PyPI 上 `huggingface-cli` 是一个真实存在的包但版本号 `0.0.0` 不太可能存在。实际上 huggingface CLI 功能由 `huggingface_hub` 包提供（通过 `huggingface_hub[cli]` extra 或直接使用 `huggingface-hub` 命令）。这可能导致 pip install 失败或在极端情况下安装到错误版本的包。
- **建议**: 移除 `huggingface-cli==0.0.0` 行，或替换为 `huggingface_hub[cli]`（如果项目实际需要 CLI 工具）。
