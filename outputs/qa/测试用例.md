## AC-01: 一键启动

> 运行启动脚本后，浏览器打开 `http://localhost:7860` 可见数字人待机画面与语音球；ASR/LLM/TTS/wav2lip/LiveTalking 各服务在 60 秒内就绪并显示连接状态。

### TC-01-01: 启动脚本按正确顺序执行

- **关联**: AC-01
- **优先级**: P0
- **前置条件**: WSL2 已安装，llama.cpp 已部署，模型已下载，Python 虚拟环境已创建
- **静态分析结果**: start-llama.bat 配置 HOST=127.0.0.1:8090，含文件存在性检查与 60 秒轮询就绪。start-livetalking.sh 检查 wav2lip256.pth 与 idle.mp4 存在性，含 60 秒就绪轮询。start-voice.sh 检查 voice.yaml 与 venv，含 90 秒就绪轮询。启动顺序（llama -> livetalking -> voice）与架构设计 §4 一致。

- **状态**: ⬜ 待执行 (需 WSL2 环境)

## AC-04: 首响延迟

> 目标配置（16GB 卡 + Qwen3-8B）下，从用户说完话到听到 AI 第一句音频的时间 P50 <= 2 秒、P95 <= 3 秒。

### TC-04-01: 拆句策略可快速送出首句

- **关联**: AC-04
- **优先级**: P0
- **前置条件**: 无
- **静态分析结果**: LLMClient.stream_chat() 使用 SSE 流式消费，每收到 token 立即 yield。ConversationPipeline.process_voice() 在收到 token 后按中文标点(。！？)实时拆句，首个完整句子立即送 TTS 合成。split_sentences() 函数按正则 `[。！？\n!?;,，]` 拆分。流程设计为"不等 LLM 全文"——即在 LLM 仍在流式输出时，首句足够长就被拆分送 TTS。
- **测试步骤**: N/A（设计审查）
- **预期结果**: 拆句逻辑存在，首个完整句子可不等全文完成即送 TTS
- **状态**: ✅ 已通过(静态分析)
- **结论**: 拆句策略设计合理。存在风险：如果 LLM 首句非常长（连续长句无标点），仍会等到有标点才拆句。但大多数大模型会按自然对话生成短句。

### TC-04-02: 首响延迟 P50/P95 测量

- **关联**: AC-04
- **优先级**: P0
- **前置条件**: 16GB 卡 + Qwen3-8B 配置，所有服务已就绪
- **测试步骤**:
  1. 修改代码在关键节点记录时间戳（录音结束 T0 -> ASR 完成 T1 -> LLM 首token T2 -> 首句文本 T3 -> TTS 合成完成 T4 -> 音频开始播放 T5）
  2. 录制 50 条测试语音（不同长度和内容，覆盖 2-15 秒）
  3. 依次送入管线，记录各段延迟
  4. 计算 T5 - T0 的 P50 和 P95
- **预期结果**:
  - P50 <= 2 秒
  - P95 <= 3 秒
- **状态**: ⬜ 待执行 (需 WSL2 环境 + GPU + 模型)
- **静态结论**: 延迟瓶颈分析:
  - ASR (faster-whisper large-v3 GPU): 预计 200-500ms
  - LLM 首 token (Qwen3-8B Q4_K_M GPU): 预计 300-800ms
  - LLM 首句完成 (取决于回复长度): 预计 +200-500ms
  - TTS 合成 (Qwen3-TTS 1.7B): 预计 500-1000ms
  - 理论最优: ~1200ms; 理论预算充足度: 可接受，但接近上限。

## AC-06: 打断

> AI 说话中途，用户重新点击语音球说话或点击停止按钮，音频与嘴型在 500ms 内停止；随后开启的新一轮对话无上一轮残留音频与残留状态。

### TC-06-01: 停止按钮触发取消令牌并终止管线

- **关联**: AC-06
- **优先级**: P0
- **前置条件**: 无
- **静态分析结果**:
  - handle_stop() 调用 pipeline.stop() -> state_machine.transition(AvatarState.IDLE)
  - AvatarStateMachine.transition() 中，当新状态为 LISTENING 或 IDLE 时，自动设置 cancel_event
  - cancel_event 在 LLMClient.stream_chat() 中每行 SSE 处理后检查，发现 is_set() 则 break
  - TTSEngine.synthesize() 在开头检查 cancel_event，is_set() 则返回 (None, 0)
  - ConversationPipeline 在处理循环中也检查 cancel.is_set()
  - reset_cancel() 在新轮开始时清除，防止上一轮干扰
- **测试步骤**: N/A（逻辑审查）
- **预期结果**: 取消令牌贯穿 LLM 流 -> TTS -> 播放的完整链路
- **状态**: ✅ 已通过(静态分析)
- **结论**: 逻辑设计正确。实机需验证实际停止延迟。

### TC-06-02: 打断后新轮无串音/串状态
